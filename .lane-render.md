## 1. From a `:::name{...}` template line to the JSON the app draws

### 1.1 The server chain

1. **The template is a product file.** A kind's manifest entry names `template:` (`src/knowledge/kinds.ts:66-92`,
   `KindDecl.template`). `renderPage` reads that file with `readFileSync(join(ctx.productFolder, decl.template),
   'utf8')` — `src/knowledge/render.ts:57`.
2. **The template is parsed into parts.** `parseTemplate` (`src/knowledge/template.ts:32-74`) splits the text into
   `{type:'text'|'block'|'problem'}` parts, each with its 1-based `line`. The directive regex is
   `/^:::([A-Za-z][\w-]*)\s*(?:\{(.*)\})?\s*$/` (`template.ts:28`); parameters are parsed by `parseParams`
   (`template.ts:77-91`); a name not in `BLOCK_NAMES` becomes a `problem` part (`template.ts:57-59`).
   Fenced code blocks are skipped (`template.ts:40-49`).
3. **Text parts** get `{{attribute}}` substitution (`substitute`, `template.ts:114-135`, called at `render.ts:72`)
   and become `{type:'markdown'}` blocks (`render.ts:73`).
4. **Block parts:** parameters are substituted with escaping off (`render.ts:82`); every `title-<lang>` parameter
   is renamed to `title` when it matches the requested `lang` and then deleted (`render.ts:83-87`).
5. **Deferred blocks:** a block whose *template name* is in `DEFERRED_BLOCKS`
   (`readonly new Set(['graph','sequence','system','modules','treemap'])`, `src/knowledge/render.ts:45`) becomes
   `{type:'deferred', block, title, line}` on a normal page request (`render.ts:89-92`). The app then asks
   `/api/k/block?id=…&line=…` for it (`src/server/knowledge.ts:107-117` → `KnowledgeProduct.block`,
   `src/knowledge/product.ts:997-1002`, which re-renders the page with `{only: line}`, `render.ts:70`).
6. **The dispatch — the one function that maps a block name to its builder:**

   ```ts
   async function renderBlock(ctx, subject, name, params, file, line): Promise<Block>
   ```

   `src/knowledge/render.ts:143-164`. It is a `switch (name)` with one `case` per block name; the `default`
   (`render.ts:162`) returns a `problem` block with the message `"<name>" is not a block of the library`.
   So a name listed in `BLOCK_NAMES` but missing here degrades to a visible problem block, not a crash.
7. **Each builder returns a shape of the `Block` union.** `BlockShape` is declared in `src/knowledge/model.ts:174-192`
   and `Block = BlockShape & { name?: string }` (`model.ts:195`); `renderPage` attaches the template's own block
   name: `blocks.push({ ...block, name: part.name })` (`render.ts:95`). That `name` is what the role logic reads
   (`wiki/app/src/knowledge/roles.ts:24-29`) — two template names can draw as one type (`implementedby` and
   `linkedfrom` both return `{type:'refs'}`, `src/knowledge/doc-blocks.ts:131`, `:198`).
8. **The page model.** `renderPage` returns `{ok:true, page: PageModel}` (`render.ts:124-136`); `PageModel` is
   `{id, kind, title, trail, blocks, resolutions, findings, notes}` (`model.ts:197-210`).
   `KnowledgeProduct.page` wraps it (`src/knowledge/product.ts:990-994`) and the HTTP route
   `GET /api/k/page?id=…&lang=…[&full=1]` answers it as JSON (`src/server/knowledge.ts:97-106`;
   route table `src/server/http.ts:575` and neighbours).
9. **The app.** `getPage` → `PageModel` (`wiki/app/src/knowledge/api.ts:9`); the model types are a hand-kept mirror
   in `wiki/app/src/knowledge/types.ts:51-72` (`BlockShape`) and `:85-94` (`PageModel`).
   `EntityPage` maps every block through `BlockView` (`wiki/app/src/knowledge/pages.tsx:77-83`) and wraps a block
   the reader's role does not open in a `<details>` (`pages.tsx:79-82`).
10. **The app dispatch:** `BlockView` (`wiki/app/src/knowledge/blocks.tsx:502-524`), a `switch (block.type)` with
    no `default`; its declared return type is `ReactElement | null`, so TypeScript fails the app build when a type
    of `types.ts` has no case (this is the app-side exhaustiveness check).
    Individual views: `Body` (`blocks.tsx:189`), `Related` (`:228`), `Calls` (`:275`), `Source` (`:350`),
    `Refs` (`:421`), `Stated` (`:448`), `Properties` (`:398`), `Deferred` (`:465`), `Problem` (`:488`);
    diagrams from `wiki/app/src/knowledge/diagrams/*` (`blocks.tsx:26-29`, `:515-519`).

## 2. A kind's ENTITY LIST page (the catalogue and the listing)

Two different pages exist; keep them apart.

### 2.1 The kinds catalogue — `CataloguePage`

`wiki/app/src/knowledge/pages.tsx:502-548`, drawn from `WikiStatus.kinds` (no graph read of its own). It groups
kinds by manifest group (`:509-512`) and shows per **kind**: name (link to the kind's list, `:536`), description
(`:537`), count plus statement count (`:538`), and origin badges (`:539`, `OriginBadges` at `:492`).
Column heads are `knowledge.catalogueCol*` (`pages.tsx:527-530`, `en.json:174-177`).
The data comes from `kindSummaries` (`src/knowledge/render.ts:193-211`, counts at `:205-209`) through
`KnowledgeProduct.status`.

### 2.2 A kind's entities — `KindPage` and `listEntities`

* **Server builder:** `listEntities(ctx, kind, {q, after, limit})` — `src/knowledge/render.ts:213-228`.
  * `markdown`/`document` kinds: in-memory filter, code-point ordering, `after` as a cursor (`render.ts:216-225`).
  * `graph` kinds: `ctx.graph.list(kind, …)` (`render.ts:226-227`) → `GraphReader.list`
    (`src/knowledge/graph-read.ts:135-…`, SQL label/key `ILIKE` filter at `:138`, key order by `COLLATE "C"`
    at `:140-141`), returning `{rows, next, total}`.
  * Reached from `KnowledgeProduct.list` (`src/knowledge/product.ts:1035-1039`) and the route
    `GET /api/k/entities?kind=&q=&after=&limit=` (`src/server/knowledge.ts:131-141`; `limit` 1..500, default 100).
* **What one row carries:** exactly `EntityRef` — `{id, kind, label, href, location?, broken?}`
  (`src/knowledge/model.ts:24-33`); `EntityListing` is `{kind, total, rows: EntityRef[], next}`
  (`model.ts:230-235`, mirrored at `wiki/app/src/knowledge/types.ts:112`).
  Rows are built by `refOfGraph` (`src/knowledge/blocks.ts:76-87` — `href` only when the manifest has the kind,
  `location` from the entity's span or, for a file, from `properties['path']` at line 1, `blocks.ts:77-86`) or
  `refOfMarkdown` (`blocks.ts:89-91`, no `location` at all). `CodeLocation` is
  `{repo, path, lineStart, lineEnd, href, web?}` (`model.ts:11-21`), filled by `locationOf`
  (`blocks.ts:70-74`).
* **What the app shows per row:** `KindPage` (`wiki/app/src/knowledge/pages.tsx:90-157`) — a filter input
  (`:132`), a total (`:133`), an empty text (`:138`), and a two-column table: **name** (`EntityName`, `:147`) and
  **place in code** (`CodePlace` or an en dash, `:148`). Column heads `knowledge.colName` / `knowledge.colPlace`
  (`pages.tsx:142`; `en.json:50`, `en.json:52`). Paging: a “more” button appends `rows` (`pages.tsx:113-125`,
  `:154`), with a stale-answer guard (`:110-119`). No kind badge and no other column.
* **Is a per-kind custom row possible today? No.** Nothing carries a per-row field beyond `EntityRef`:
  * the manifest has no field for it — `KIND_KEYS` is a closed set
    (`'template','source','folder','file','title','attributes','relations','labels','group','origin','description','identifier','terms'`,
    `src/knowledge/kinds.ts:135`), and a kind carrying another key is a finding: `"<key>" is not a field of a kind`
    (`kinds.ts:264`); a top-level unknown key is the same kind of finding (`kinds.ts:180`).
  * the listing type has no room — `EntityListing.rows: EntityRef[]` (`model.ts:230-235`).
  * the app table is fixed at two columns (`pages.tsx:140-152`).
  Where such a column would be added, in this order:
  1. `src/knowledge/kinds.ts:135` (new manifest key) plus its parse/validation near `kinds.ts:200-230`;
  2. `src/knowledge/model.ts:230-235` (a row type richer than `EntityRef`, e.g. `{entity, cells[]}`) and the
     mirror `wiki/app/src/knowledge/types.ts:112`;
  3. `src/knowledge/render.ts:213-228` (compute the cells; for graph kinds the data already exists as edges —
     `ctx.graph.neighbors` / `edgesOf`, used by `callBlock`, `blocks.ts:286-291` — and the document-side
     “implemented by” logic is `implementedByBlock`, `src/knowledge/doc-blocks.ts:74-132`);
  4. `wiki/app/src/knowledge/pages.tsx:139-153` (draw the columns; column heads as new `knowledge.*` keys in
     `en.json`/`ru.json`, e.g. beside `en.json:50-58`);
  5. the route needs no change (`src/server/knowledge.ts:138-140` passes the listing through whole), and
     `test/knowledge-server.test.ts:225-231` plus `test/knowledge-render.test.ts:425-433` are the listing tests.
  Note the product declares per-kind columns today only in the **page template** (a block), not in the list.

## 3. What a contract node and an operation node carry today

### 3.1 Node shapes (the extractor's own schema)

Keys and kinds: `src/extract/contracts/schema.ts:14-22` (kinds) and `:40-43`:
`contractKey(path) = 'code.contract:<path>'`, `operationKey(path, op) = 'code.operation:<path>#<METHOD>:<template>'
(HTTP) or `<path>#<package>.<Service>/<Rpc>` (proto)`. Channels and messages: `channelKey(name)`,
`messageKey(path, name)` (`schema.ts:46-49`).

**`code.contract`** — one node per contract file, from the three readers:

| reader | node builder | properties | span |
|--------|--------------|------------|------|
| OpenAPI | `openApiNodes`, `src/extract/contracts/openapi.ts:95-105` | `{format:'openapi', specVersion?, version?}` | **none** |
| protobuf | `protoNodes`, `src/extract/contracts/proto.ts:82-88` | `{format:'proto'}` | **none** |
| AsyncAPI | `asyncApiNodes`, `src/extract/contracts/asyncapi.ts:92-104` | `{format:'asyncapi', specVersion?, version?}` | **none** |

`label` is `info.title` / the proto `package` / the path. The **file path exists only in the key** — no reader
puts it in `properties`, and no reader stores the raw text or any parsed JSON. The parsed document is used inside
`readOpenApi`/`readAsyncApi` (`openapi.ts:43-92`, `asyncapi.ts:40-89`) and thrown away; only the summary fields
above survive into the nodes.

**`code.operation`** — one node per operation/rpc:

| reader | builder | properties | span |
|--------|---------|------------|------|
| OpenAPI | `openapi.ts:106-118` | `{method, path, operationId?, summary?, public}` | yes: `measure.span(path, …range…)`, `openapi.ts:68-78` |
| protobuf | `proto.ts:89-103` | `{rpc, service, package?, input, output}` | yes: the rpc line, `proto.ts:62` |
| (AsyncAPI has no operation node) | | `code.channel`, `code.message` instead (`asyncapi.ts:105-127`: `{contract, description?, protocol?}` and `{channel, eventTypes?}`) | none |

Edges: `code.declares` from the contract to each operation/channel/message
(`src/extract/contracts/index.ts:143`, collected at `:113`, `:123`, `:126`, `:134`), `code.carries`
channel→message (`index.ts:127`), `code.serves` / `code.calls-remote` for the route and client linking.

### 3.2 How a span becomes a wiki location

`ExtractedNode.span` is stored as the node's `span` property by the extract driver:
`properties: { ...node.properties, ...(node.span === undefined ? {} : { span: spanProperty(node.span) }), recordKey: node.key }`
— `src/extract/driver/index.ts:571` (`spanProperty` at `:168-170`). The wiki reads it back with
`spanOf(properties['span'])` (`src/knowledge/graph-read.ts:71-77`, used at `:85`), and `GraphEntity` is
`{key, kind, label, properties, nodeIds, scope, span?}` (`graph-read.ts:24-35`).
Because a contract node has no span, `refOfGraph` finds no location for it either (`blocks.ts:77-86`), so
**a contract's row in a kind list shows “–” in the place column and its page has no place**.

### 3.3 Is the contract file's raw text available at read time?

**Yes for the bytes, no for the coordinates that `:::source` needs today.**

* `RenderContext.readSource(repo, path)` — `src/knowledge/blocks.ts:51`, implemented in
  `KnowledgeProduct.context()` as `readSource` (`src/knowledge/product.ts:818-834`):
  * `repo === null` (the product repository): guards on `insideFolder`, dotfiles and `repos/`, `realpath` +
    `statSync().isFile()` + a 2 MB cap, then `readFileSync(real, 'utf8')` (`product.ts:819-829`);
  * otherwise the pinned repository: `gitBlob(join(product.folder,'repos',repo), pin.commit, path)`
    (`product.ts:831-833`), and `gitBlob` is `git cat-file blob <commit>:<path>` with a 64 MB buffer
    (`product.ts:138-145`). A repository with no pin yields `undefined` (`product.ts:832`).
* The repository for a graph entity is `ctx.repoOfScope(entity.scope)`, i.e. the pin whose `scope` matches
  (`product.ts:817`); every extracted node is published under the repository node as its scope
  (`src/extract/driver/index.ts:622`), so a contract node's scope is the code repository it was read from.
* **The `source` block** is `sourceBlock` (`src/knowledge/blocks.ts:299-319`): it takes the span from
  `entity.span ?? properties['path']`-at-line-1 (`blocks.ts:302`), maps the scope to a repo (`:304`), and reads
  `await ctx.readSource(repo, span.path)` (`:305`; the shown text is capped at `SOURCE_BLOCK_LINES = 200`,
  `blocks.ts:297`, `:310`, `:316-317`).
  **Consequence: `:::source` on a `code.contract` page today returns a `problem` block** —
  “`<key>` has no declaration span and no path: nothing to show” (`blocks.ts:303`). A raw-spec view must either
  (a) make the contract extractor give the contract node a `path` property and a span (one-line change per reader,
  `openapi.ts:96-105`, `proto.ts:83-88`, `asyncapi.ts:93-104`), or (b) add a block that derives the path from the
  key (`entity.key.slice('code.contract:'.length)`) and calls `ctx.readSource` — the bytes are there either way.
* The **source page** reads the same bytes through `KnowledgeProduct.source` (`product.ts:1094-1100`) and the route
  `GET /api/k/source?repo=&path=` (`src/server/knowledge.ts:155-167`, 2 MB cap at `:165`), which the app draws in
  `SourcePage` (`wiki/app/src/knowledge/pages.tsx:160-209`).
* Head shapes for a new block: `src/extract/contracts/openapi.ts:15-31` (`OpenApiOperation`, `OpenApiContract`),
  `proto.ts:15-27`, `asyncapi.ts:13-26`.

## 4. Lazy dependencies and localisation in the wiki app

### 4.1 Lazy loading — yes, two precedents

* **Mermaid:** `mermaidModule ??= await import('mermaid')` inside the draw effect
  (`wiki/app/src/diagram.tsx:53`, module cached at `:20-21`), sized for a heavy renderer used on few pages.
* **Shiki:** the core, engine and two themes are imported together on first use
  (`wiki/app/src/knowledge/shiki.ts:39-50`), and each language grammar is a dynamic import loaded the first time
  that language is met (`shiki.ts:17-31`, loaded at `:64-68`); a text over `COLOR_LIMIT_CHARACTERS = 300_000`
  keeps the plain scanner (`shiki.ts:34`, `:61`).
* Both patterns degrade to plain text on failure (`diagram.tsx:67-70`, `shiki.ts:59-62`).
* Build: Vite (`wiki/app/package.json` `"build": "vite build"`); the served `wiki/app/dist` is hash-stamped and
  rebuilt when the app's sources change (`src/product-wiki/app.ts:32-129`). So a new dependency is a
  `wiki/app/package.json` change plus a rebuild — and, if it is heavy, a dynamic import like the two above.

### 4.2 Locales

* Files: `wiki/app/src/locales/en.json` (473 lines) and `wiki/app/src/locales/ru.json` (473 lines).
* Wiring: `i18next` + `react-i18next` initialised once with both catalogues as `resources`, `fallbackLng: 'en'`,
  `supportedLngs: ['en','ru']`, `escapeValue: false` — `wiki/app/src/i18n.ts:26-36`; the chosen language is kept in
  `localStorage` under `madarch-wiki-language` (`i18n.ts:7`, `:38-44`) and set by `setWikiLanguage`
  (`i18n.ts:46-48`). `normalizeLanguage` maps anything starting `ru` to Russian, else English (`i18n.ts:9-11`).
* Usage example: the block table heads are
  `<TableHead>{t('knowledge.colName')}</TableHead><TableHead>{t('knowledge.colKind')}</TableHead>
  <TableHead>{t('knowledge.colPlace')}</TableHead>` — `wiki/app/src/knowledge/blocks.tsx:252-254`, with
  `"colName": "Name"` at `en.json:50` and `"colName": "Название"` at `ru.json:50`.
  Interpolated example: `t('knowledge.showing', { shown, total })` (`blocks.tsx:267`) with
  `"showing": "Showing {{shown}} of {{total}}."` (`en.json:58`).
* Both catalogues must stay in step: `wiki/app/src/i18n.test.ts:14-16` compares the leaf key sets.
* **Kind names are not locale keys.** They come from the product manifest's `labels` and are drawn by
  `useKindName` / `kindNameOf` (`wiki/app/src/knowledge/kind-names.ts:15-28`, fed by `KindSummary.labels`,
  `wiki/app/src/knowledge/types.ts:106-107`); a kind without labels falls back to the key made readable
  (`wiki/app/src/knowledge/routes.ts:108-119`).
* **Block titles are not app strings either.** A template writes them, in both languages, as
  `title="…" title-ru="…"` (`src/knowledge/seed.ts:20-23`), and the server picks `title-<lang>` at render time
  (`src/knowledge/render.ts:83-87`). So a new block's *title* needs a template edit, its *own* words (columns,
  empty states) need `en.json`/`ru.json`.

## 6. Facts that constrain a plan for two new page features

1. A block is a *template name* plus a *block type*; several names may share one type (`children`→`related`,
   `implementedby`/`linkedfrom`→`refs`). Reusing an existing type means only items 1–2 of the table in §1.2
   (plus tests) change on the server; the app needs no edit.
2. The server dispatch has a `default` (`render.ts:162`), so a missing builder degrades silently to a `problem`
   block; the app's switch is exhaustive only through its return type (`blocks.tsx:502`). A test per new block is
   therefore required, not optional.
3. Anything heavy that reads the graph should join `DEFERRED_BLOCKS` (`render.ts:45`) — the page then answers at
   once and the app fetches that one block by template line (`pages.tsx` → `Deferred`, `blocks.tsx:465-486`).
4. A contract page has no place and no `:::source` today: no span, no `path` property, path only in the key
   (§3.1, §3.3). Any raw-spec feature starts by giving the contract node coordinates or by deriving the path from
   the key.
5. The entity list is fixed at `EntityRef` rows and two columns; per-kind extra columns need a new manifest key
   (`kinds.ts:135`), a richer listing row (`model.ts:230`, `types.ts:112`), the builder (`render.ts:213`), and the
   table (`pages.tsx:139-153`) — five places, plus locale keys and the two listing tests.
6. Strings split three ways: block titles in the product template (`title-`/`title-ru`), kind naming in the manifest
   `labels`, and the app's own words in `locales/en.json` + `locales/ru.json` (kept in step by `i18n.test.ts:14`).
