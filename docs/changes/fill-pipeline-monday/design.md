# Fill pipeline design — Monday slice

## Unit and resume model

The run is a JSON manifest at `.madarch/fill/run.json`; unit records live in `.madarch/fill/units/<unit-id>.json`, outputs in `.madarch/fill/outputs/<unit-id>/`. The manifest pins run id, product repo path, starting default-branch commit, registry byte hash, agent branch, schema version, status and created/updated times. These are local operational state and derived outputs, not product truth (decisions 0017, 0023); product pages remain Markdown committed to product git. On PGlite landing, the same typed records move behind its storage interface; no migration makes `.madarch/` authoritative.

A unit has stable `id`, `stage`, `scope`, `inputHashes` (code tree/blob hashes, registry hash, and hashes of upstream outputs), `status` (`pending`, `running`, `complete`, `blocked`, `stale`), `attempt`, `outputPaths`, `startedAt`, `finishedAt`, `error`, and `agentUsage` (`elapsedMs`, `inputTokens`, `outputTokens`, `estimatedCost?`). Write each JSON file through temp-file + fsync + atomic rename. At startup, a `running` unit whose process is gone is requeued; a `complete` unit is reused only if all input hashes still match; otherwise it becomes `stale`. No partial output is published as complete. At stage boundaries compare the default-branch HEAD and current inputs with the pinned snapshot; invalidate only units whose direct hashes changed, then transitively invalidate consumers. New changes never silently retarget the active run. Emit stage/unit totals (reused, run, stale, blocked) in report.

The code checkout is a read-only input snapshot. A separate product-repository worktree owns branch `madarch/fill/<run-id>`; only the controlled writer applies generated Markdown there. Run and unit JSON plus event journal are atomic files under `.madarch/` until PGlite lands. Product-authored Markdown and claims live in product git; no database is more authoritative than git (0017, 0023). Facts, intent evidence and assumed meaning stay distinct; this design does not write extracted facts into an intended architecture model (0004, 0005).

## Stages and real dependencies

1. **Inventory** (no agent): enumerate repositories, default branch and file-language counts; choose bounded units, test configured `claude` / `codex` availability, estimate work. It pins the read snapshot.
2. **Structural index**: tree-sitter files, symbols, imports, entry points, call edges, comments and task keys, each anchored to source blobs. Depends on inventory.
3. **Claims**: claims from the repository's own README/docs/comments/commits and task keys; sources are recorded. Depends on inventory and indexed anchors. Outside-link fetching is explicitly after Monday.
4. **Code map**: bottom-up components, interactions and state transitions from index. Depends on index; may run in parallel with claims after index.
5. **Synthesis**: overview and main registry kinds reconcile claims against code; multiple bounded generation passes and a critic pass per page/unit. Depends on code map and claims. Output is proposed Markdown, not an accepted intended model.
6. **Question review**: detect typed questions, attach dependencies and ranking, calculate next-step hints. Depends on synthesis and claims. A person's answer triggers recompute of dependent units.

Stages 1-3 then 4 are serial where noted; after index, claims and code map run in parallel. Synthesis waits for both; question review follows synthesis. The first slice deliberately excludes automatic update after default-branch commits, editor acceptance/rejection, outside-link fetching and automatic agent closure of questions.

## Headless agent calls and containment

Invocation is an argument vector, not shell-concatenated prompt. Claude: `claude -p --output-format stream-json --permission-mode plan --permission-prompts none --add-dir <read-only-code-snapshot> <prompt>`. The product agent worktree is the process cwd only for the controlled writer; extraction calls run with read-only tools and no product write directory. Do not use `--dangerously-skip-permissions` or `bypassPermissions`. Claude CLI help on this machine confirms `-p`, `stream-json`, `plan`, `--permission-prompts none`, `--add-dir`, and `--disallowed-tools`; implementation should explicitly deny `Write`, `Edit`, and `Bash` for extraction and validate tool events before accepting output. Codex: `codex exec --json --sandbox read-only --cd <code-snapshot> <prompt>`; help confirms JSON events and read-only sandbox. Generated page writes go through madarch's validated apply operation in the agent worktree, never an agent shell on the code checkout. Credentials and arbitrary network access are not granted. Preserve raw event lines in per-unit logs; normalize message/tool/result events into `{runId,stage,unitId,seq,at,type,summary,usage}` and redact secrets before UI display.

The serving app consumes normalized events and atomic run/unit state. Right-hand panel shows stage/unit progress, completed/reused counts, current agent activity, and Pause/Stop. Pause prevents dispatch of new units and allows the active unit to reach a checkpoint; Stop prevents dispatch and terminates active child processes, preserving completed units. The panel updates from the local event journal/file watcher. In the background-server product route, the panel and question/page links are rooted at `/products/<name>/`, with API calls under `/products/<name>/api/...`; `madarch serve` retains the empty base route. The wiki app reads its base at startup, so route generation and API clients must use that startup base rather than assuming `/`.

## Branch, stage commit and human edits

Create one product agent worktree and branch `madarch/fill/<run-id>` from the product default branch. Each stage writes only its generated pages and provenance records, validates them, then makes one stage commit. After each stage commit, compare its touched paths and base with the current default branch. Merge only if no conflict and no human edit changed a target page since the stage input hash. If a person changed a page, keep the human version, do not overwrite or auto-resolve; mark the corresponding unit `blocked` with `human-edit-wins` and expose a review action. A clean stage is merged/pushed by the product git write path, so live wiki readers see each accepted stage as soon as it lands. Never rewrite the person's branch or force-push.

## Claims, sources and assumptions

Claim record fields: `id`, `kind` (registry kind), `text`, `layer` (`fact`, `intent-evidence`, `assumed-meaning`), `unitId`, `sourceIds[]`, `verification` (`verified|unverified`), `confidence`, `createdAt`. Source record fields: `id`, `address` (repo-relative path or URL), `version` (commit/blob id or fetched validator), `anchor` (line range, symbol, heading, or record id), `readAt` (UTC ISO timestamp), `sha256`, `mediaType`. For repository documents, `version` is the pinned commit and hash is the exact bytes read. Claims must have sources; meaning inferred beyond evidence is `assumed-meaning`, visibly marked **Unverified**. Do not describe absence as fact unless the index reports complete coverage of the relevant scope (0005). Kinds and extraction strategy come from `docs/kinds.yaml` registry, not engine constants (0021 and `src/product/completeness.ts` external-data precedent). Every registered kind either has entities or a question with reason why no entities were found.

## Open questions, answers and next step

Question Markdown records use generic front matter plus `type`, `status`, `depends-on`, `rank`, `evidence`, `answer` and `updated-at`. Types: `meaning`, `contradiction`, `undocumented-behaviour`, `assumption-check`, `term`, `unverifiable`, `decision-rationale`, `access-or-document-needed` (with a `missing` field set to `access` or `document`, so the need is explicit). `depends-on` names claim/page/unit ids; rank is the count of distinct dependent pages/units (descending), stable id ascending as tie-break. Rank is a recommendation, not a task priority claim. Each page shows questions that depend on it. For Monday, a person answers via the wiki's existing Markdown write path; answer is committed to product git and invalidates dependent unit hashes. Agent auto-closing after later evidence is out of slice.

Every page receives a simple next-step object `{action,reason,target,rule}`. Rules in strict order: (1) answer highest-ranked unresolved blocking question; (2) review an unverified assumption; (3) fill a missing required registry kind/link; (4) use registry-provided next-step hint; (5) generic “Review this page and its sources”. Rules inspect registry data and current page state; no kind names are hard-coded. The rendered label and reason appear on the page.

## Monday leaves and parallel plan

The leaf tasks under `madarch-tzte`, `madarch-p45j`, and `madarch-co2d` divide runtime, agent UI, fixture/extraction, questions and next-step logic. Inventory/index can be built independently of question UI. The training generator (`madarch-p45j.1`) and core run-state/runtime (`madarch-tzte.2`) can proceed in parallel; agent invocation/panel follows the event and runtime contract. Claim extraction depends on the fixture and index output; synthesis depends on claim extraction and code map; first checkpoint report depends on the completed pipeline and fixture. Question/next-step implementation can build against the generic data types and is only gated on claim/page identifiers, not on code extraction internals. This is sized for 2–3 workers through Sunday night; no task claims broader milestone outcomes.
