# The product's diagrams in the wiki: the Architecture section

## Intent
The owner's feature E (note-two-paths.md, 2026-10-11 ~16:40 MSK): the old
wiki rendered the product's views (LikeC4, Mermaid), but the new React app
shows none. After this change the served wiki has an Architecture section —
the Design stage's part of the life cycle: one page per view of the
product's model with its diagram drawn in the browser (Mermaid from the
shared renderer's own source; the LikeC4 webcomponent beside it, the same
bundle the static wiki's build generates), the model's elements as pages
with their relations and the pages that name them, and the model's compile
errors on the section's page, each naming file, line and path — an
uncompilable model never blanks the wiki. The product's own model (`model/`
of the product repository) merges with each declared code repository's own
`madarch/` model under `repos/`; a repository that is declared but not
checked out is a named note, never a silent omission.

Stories:
- As an engineer reading a product's wiki, I open Architecture from the
sidebar and see the model's views as real diagrams, drill from a view into
its children, and reach every element's page with its relations.
- As an engineer reading a document, a mention of an element's id links me
to that element's page.
- As an engineer whose model does not compile, the Architecture page names
every error with its file, line and path, and the rest of the wiki works.

## Out of scope
Editing the model from the wiki (the editor is madarch-j0a); the archify
tab; per-environment and per-state view pickers; element pages beyond
relations and links (zones and data categories stay with the static wiki's
pages); the repositories section (madarch-iuc.16 / feature D).

## Rationale
The wiki capability already compiles and renders models (src/model,
src/render, src/wiki); this change reads the same pipeline's outputs into
the served app instead of building a static site. The merge rule follows
the set's refinement model: the product's files are the spine, repository
files join them, and duplicate ids are a named error — never an override.
The conservative document-to-element rule is the backlinks rule the
product's documents already use: the id as written, word-bounded.

## Design and decisions
The model is read fresh at every ask (the pages rule); the bundle is one
JSON answer (`/api/architecture`) and the LikeC4 webcomponent is one script
(`/api/architecture/likec4.js`), generated by the pinned `likec4` of the
checkout into the wiki's per-user cache root, named by the workspace's
content hash (the static build's own naming), so two asks of one model
share the folder and a changed model regenerates. The views, their Mermaid
sources and their relation tables come from the shared renderer
(`renderModel`) at the fixed moment, never the clock. Element pages are
computed from the compiled model; the document-to-element links are
computed with the same word-boundary rule the backlinks use, and only the
first mention of each element id on a page is wrapped. The section's chrome
follows the reading shell's tokens in both themes; the Mermaid theme
follows `prefers-color-scheme` live.
