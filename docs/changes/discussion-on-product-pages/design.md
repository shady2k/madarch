# Discussion first-comment vertical slice design

Change: discussion-on-product-pages
Task: madarch-y781.2.1
Base: 195aaff555992397e802e522dc136d592662c088

## Outcome and drivers
A reader on a locally served product wiki selects text, saves a comment, sees it beside the marked range, and sees it again after reload. The product repository is the authored source of truth (decision 0017); the graph remains derived (0023). Published v1 message and marker syntax are fixed. The product server currently serves its selected product read-only; its pages are fetched from that product per request. This stage deliberately adds one local write capability.

Functional seams: rendered selection -> source range -> paired marker insertion; v1 message file; validated write endpoint; one git commit per action and push/retry; reloadable reads; adjacent comment display. Explicit constraints: no external repository fixtures, no new message schema, no unrelated edits in a product checkout, and no authentication/server-mode scope. The current server binds loopback by default and serves one product chosen at startup.

## Quality scenarios
- Integrity: malformed paths, stale or ambiguous ranges, invalid ULIDs/front matter, or pre-existing working-tree changes cause a refusal before any product write; assert recursive path/byte snapshots including ignored files, index tree, HEAD and local remote refs unchanged.
- Markdown safety: a selected range crossing inline Markdown widens to a complete valid word/element range; rendered text remains unchanged apart from hidden comments.
- Retry safety: a push rejection never overwrites remote work; retry is bounded, rolls back only the operation-owned local commit before fetching, and reapplies once only when the selected source range still matches. A final failure is visibly “not sent” and leaves the draft recoverable.
- Usability: the first comment appears beside its selected text on reload, at desktop layout; replies and responsive panel are later stages.

## Existing architecture
`wiki/app` renders product pages from `/api/page`; `src/server/http.ts` owns one route table; `src/server/wiki-app.ts` builds product wiki handlers; `ProductWiki` reads pages from the chosen working tree. `src/product/discussion-contract.ts` parses v1 front matter and validates marker pairs. `src/product/git.ts` safely strips inherited `GIT_*` selectors for git commands, but currently exposes only generic process execution and repository identity helpers. The UI page reader renders ReactMarkdown in `wiki/app/src/view.tsx`, called from `PageReader` in `app.tsx`.

## Options
1. Browser writes files or invokes git directly. Rejected: the browser cannot safely own a product path or git identity, and breaks the server's product boundary.
2. Add an explicit same-origin server route for one discussion action. The route validates the exact product-relative page and v1 message, checks a clean product worktree, applies markers and one message atomically, commits once and pushes; the existing page API then reads the committed working tree. Rejected-push handling pulls only fast-forwardable state and revalidates the exact original source; otherwise it returns a retryable not-sent result. Chosen: smallest route through the current product server, same authored source, no second writer or persistence store.
3. Build a background write queue/workspace service before the UI. Rejected for this local product-only feature: introduces durable queue ownership, retry lifecycle, and operational state not required by the agreed one-action synchronous write path.

## Decision and mechanism
Use option 2, with stricter filesystem and retry boundaries. A discussion writer beside the v1 contract validates product-relative paths, ULIDs, current source, message metadata and markers before writes. The requested document must resolve beneath the product root, and every traversed path component is checked with `lstat`; symlinks are refused, the final target must be a regular file, and writes use an exclusive temporary file in the same verified directory followed by atomic rename. A per-product in-process mutex serializes discussion writes. Before starting, require an entirely clean index and working tree, including untracked non-ignored files; after acquiring the lock, repeat the cleanliness and page-content checks. Stage only the exact page and new message path, never `git add -A`. The fixture tests compare recursive file paths and bytes (including ignored files), index tree, HEAD and local remote refs before/after refusal and failure cases.

Create a unique message ULID and UTC timestamp; validate the constructed file with `parseDiscussionMessage` and the edited source with `scanDiscussionMarkers`. The action commit includes only the marker edit and its new message. Push once. On a rejected push, do not pull on top of the local action commit: save its two exact output byte sequences in memory, reset only that operation's known commit to its recorded parent, fetch `origin` without modifying the worktree, require a fast-forwardable remote and clean tree, and compare the current source at the selected range with the original quote/context. If it still matches, reapply the prepared marker/message action against the remote tip, create a fresh single action commit, and push once more. If any step fails, remove the operation's exact temp/output files and leave the product at the remote tip if it advanced; return a retryable unsent draft to the caller. Never reset, checkout or restore paths not created by this operation. If local rollback cannot be proven safe, stop and return an explicit recovery error rather than deleting or overwriting user data. This ensures one successful action commit, no duplicate commits and no unrelated files staged.

Selection mapping is a pure prefactor. ReactMarkdown source positions use UTF-16 code-unit offsets, as do DOM Range offsets; marker offsets are therefore source code-unit indices. The saved quote and `before`/`after` context are computed from decoded rendered text using Unicode code points (the v1 contract's context limit), while exact source slices are retained for the edit. A rendered leaf carries source positions and an explicit mapping from each rendered text boundary to a source boundary. Entity decoding, escapes and syntax that make that mapping non-bijective are handled by a pinned source-map routine; if a DOM boundary maps to multiple source boundaries or splits a grapheme/inline construct, the selection expands to the smallest complete inline element/word range that preserves rendered text. If no unique valid range exists, selection fails closed with no save. Fixtures include astral Unicode, combining text, entities, escapes, emphasis, links, nested inline syntax and boundaries at both ends.

The route accepts only same-origin requests to the product already opened by this server. It accepts no caller-supplied product folder, remote URL, git command or arbitrary path. The remote is that repository's existing `origin`; absence or push failure returns not-sent and preserves the draft. No document or message body enters logs.

## Design review
A fresh gpt-6-luna reviewer found four blocking omissions before implementation: symlink/path race and concurrent writes; unsafe pull-on-top-of-local-commit retry; unspecified DOM/source offset units and Unicode context; and git-status-only tests that could miss writes restored or ignored files. The decision and test mechanisms above address each: lstat/no-symlink and atomic replace, per-product serialization and repeated clean-tree checks; rollback only the operation's known commit before fetch and reapply once after source verification; explicit UTF-16 code-unit vs Unicode-code-point rules with fail-closed mapping fixtures; recursive filesystem/index/HEAD/remote-ref snapshots. No implementation began before these design corrections.

## Risks
The main technical risk is mapping DOM offsets to raw Markdown around entities and inline syntax. The prefactor defines UTF-16 source offsets, Unicode-code-point quote/context, exact source-boundary mapping and fail-closed ambiguity, covered by fixture tests before writes depend on it. The product's local git identity or remote can be absent; then no success is reported and no partial files remain. Push retry can encounter a changed anchor; it does not guess or overwrite and instead returns the preserved draft as not sent. Symlink swaps and concurrent server writes are bounded by no-follow path checks, atomic same-directory replacement, a per-product write lock and revalidation immediately before staging.
